# MuJoCo Vision-Guided Multi-Object Pick-and-Place

A beginner-friendly Digital Image Processing demonstration: choose a color, inspect camera processing, click a matching instance if needed, and let a simulated Panda physically grasp and place it in a tray.

## Windows setup

Use **64-bit Python 3.12**, including Tcl/Tk (the normal python.org Windows installer includes it). Extract this project ZIP, open PowerShell in the extracted `project` folder, and run:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

No PowerShell activation or policy changes are needed. `requirements.txt` pins the versions actually used. `requirements.lock.txt` also records transitive dependencies. MuJoCo uses a local OpenGL display; use an ordinary Windows desktop with a working graphics driver. The OpenCV package is used for processing, while Tk provides the one dashboard. A separate native MuJoCo viewer is optional.

After setup, you can also double-click **Launch_Demo.cmd**. If an earlier dashboard is still open, close it and launch again to load the current source.

In the current shared workspace, a tested environment exists one folder above this README:

```powershell
.\.venv\Scripts\python.exe project\app.py
.\.venv\Scripts\python.exe project\run_tests.py
```

For a fresh extracted project, run tests with:

```powershell
.\.venv\Scripts\python.exe run_tests.py
```

Tests render real MuJoCo images even though no visible viewer is required. A working OpenGL graphics context is still needed. If `mujoco`/`cv2` imports fail, run the install command with the **same** interpreter used to launch the app. If Tk is missing, repair the Python installation with Tcl/Tk selected. On remote desktops or headless systems, restore a local graphics desktop rather than assuming the renderer will work.

## Live demonstration

1. Start with **BLUE**. All four boxes are visible; two share the color.
2. Enable **Simulated noise (8%)** to show repeatable salt-and-pepper noise (seed 42).
3. Leave **Step-through** on. Click **Detect / start stages**, then **Next stage**.
4. Step through camera, noise, median filtering, selected-color mask and rectangular outline.
5. At the detection stage, click the particular blue box in the **RGB camera** preview. One matching region is selected automatically; multiple regions require a click. Orange marks the chosen outline.
6. Continue to the world estimate and reachability stage. The robot remains stationary until the checks pass.
7. Click **Next stage** again, or **Run pick-and-place**, after reachability passes.
8. Watch approach, alignment, descent, finger closure, lift, transfer, release, retreat and return. **Pause / resume robot** freezes simulation physics during movement.
9. **Reset** restores the initial scene. Reset before another pick or placement.
10. Choose **YELLOW**, which is absent, to show a missing-target rejection. No movement starts.

With Step-through off, Detect shows the pipeline together and Run starts after validation. The dashboard contains RGB, simulated noise, filtered image, selected-color mask, detection overlay, scene, controls and status. The native **MuJoCo viewer** button opens a separate orbitable robot view. During motion the dashboard shows a locked camera estimate; later camera masks can change because the hand hides the object.

The **Record MP4** checkbox saves `outputs/live_demo.mp4` with labeled image-processing panels. The supplied `outputs/actual_demo.mp4` is generated by the completed test run. Its initial explanatory hold uses a noisy processing frame; subsequent frames show the real evolving simulation. The simulation steps at 0.002 seconds, with recorded frames every 25 physics steps (20 fps). The GUI may run slower than real time while rendering and encoding; it remains responsive through event updates. Rendering latency is not a measured real-robot control rate.

The final supplied recording was refreshed with `record_demo.py`: one additional physical blue-box run with simulated noise enabled throughout and current camera images in the final hold. `outputs/recording_result.json` records its independent validation. Run `python record_demo.py` in the same environment to reproduce this short recording without running the broader suite.

## Repositioning and validated workspace

Select `blue`, `red`, `green` or `blue2`; enter X/Y in **metres**, yaw in **degrees**, and click **Validate and place**. Allowed box-centre bounds:

- X: 0.38 to 0.67 m
- Y: -0.08 to +0.18 m
- Yaw: -85 to +85 degrees
- Centre separation: at least 0.095 m

Bounds alone do not authorize a pose. Each placement additionally solves all motion waypoints under joint limits and checks sampled robot/table clearance. A 27-pose grid samples the corners/interior at yaw -85, 0 and +85 degrees. See `outputs/workspace_checks.json` for actual outcomes. This is a conservative **test workspace**, not a proof that every configuration in the Panda's theoretical workspace is safe. Continuous collision checking, arbitrary obstacle avoidance, piled objects and changing box dimensions are outside scope.

Only setup/reset methods edit object free-joint positions. `pick()` never edits an object's pose and creates no weld or grasp attachment constraint. Lifting and transport use the two simulated fingers, friction, contacts and gravity. The Panda model retains its normal equality constraint coupling finger movement; that is not an object attachment.

## How pixels become a target

`vision.py` receives only an RGB image and camera calibration. It never receives object body positions.

1. A 640 x 480 RGB image is rendered from the fixed `overhead` camera.
2. Optional salt-and-pepper noise changes 8% of pixels using a fixed random seed.
3. A 3 x 3 median filter replaces each pixel channel with the neighborhood median. It reduces impulse noise, but can soften edges and does not remove all kinds of noise.
4. Convert RGB to OpenCV HSV. Selected hue intervals plus saturation/value thresholds create a binary mask. Blue H=90..135, green H=35..85, red H=0..10 or 170..179; saturation >=90, value >=50. OpenCV's hue scale is 0..179.
5. A 3 x 3 opening removes isolated foreground specks; closing fills small gaps.
6. Contours must meet area (150..5000 pixels), minimum side (8 pixels), aspect ratio (1.35..3.2) and rectangular fill (>0.72) checks. The reported fill ratio is a shape-validity score, **not a calibrated probability**.
7. `minAreaRect` gives image corners. Choose its longest edge, map both endpoints through camera calibration, and use `atan2(world_dy, world_dx)` for world yaw. Normalize to [-90,+90) degrees: a plain rectangular box is equivalent after 180 degrees. Color alone does not determine angle. Squares do not have a unique long edge and have ambiguous yaw.
8. Map the centre pixel along a camera ray to the **known box-top plane**, then subtract half the box height to report its centre. Table top z=0.23 m; all boxes height=0.04 m; box top z=0.27 m. Camera position=(0.52,0,1.4) m, directly overhead, vertical FOV=45 degrees, no lens distortion.

The focal length is `f = image_height / (2*tan(vertical_FOV/2))`. With pixel centre `(cx,cy)=((width-1)/2,(height-1)/2)`, a camera ray is `R * [(u-cx)/f, -(v-cy)/f, -1]`. Intersect `C + t*ray` with z=0.27. The same ray-plane computation uses the actual camera matrix, so a calibrated tilt could be represented; the tested scene is directly overhead. Different object heights require their correct top plane or depth. Outlines can include colored side faces; this and pixel quantization produce small measured errors.

Vision supplies the estimated centre/yaw. DLS IK maps desired hand poses to seven joint targets. A smooth joint-space interpolation sends those targets to the Panda's position servos. Those servos apply torques and execute motion through physics. The waypoint sequence is simple planning, not a general obstacle planner. IK is not image localization, and the controller does not identify the color.

## Measured tests and outputs

**Run measured test mode** in the dashboard starts a separate test simulation and shows a summary on completion. It overwrites the generated outputs; keep a copy if needed. The CLI also runs `run_tests.py`. The tests cover three target colors among distractors, the second blue instance, several positions/yaws, 0/3/8% simulated noise, physical lifting/release, missing target, outside-workspace target, far-pose IK failure, median filtering, opening/closing and a reachability grid.

- `results.csv`: each completed test and its measured outcome
- `summary.json`: aggregate measured results
- `coordinate_log.json`: image estimates compared with ground truth **after** detection; final body positions, measured lift and finger opening
- `workspace_checks.json`: actual preflight grid checks
- `baseline.json`: bounded run of the original upstream pick-and-place
- `camera.png`, `noisy.png`, `filtered.png`, `raw_mask.png`, `mask.png`, `overlay.png`: individual processing stages
- `noise_*.png`: optional-noise comparison stages
- `dashboard.png`, movement screenshots, `placed.png`, `failure_*.png`: actual simulation output
- `actual_demo.mp4`: actual physical pick-and-place with processing panels
- `initial_failed_run/`: preserved first failed blue-threshold test results

All reported position/yaw errors are independent validation measurements in `validate.py`. Simulator ground truth is never used to pick the detected instance or as a movement target. Test fixtures place known poses before capture; a fixed image-order instance rule selects leftmost (or rightmost for the second-blue test) before ground truth is evaluated. Success requires the selected body to lift by >8 cm, end inside the tray at the expected height, and have open fingers after release. This finite test set does not establish a general success rate for arbitrary scenes.

The optional `baseline_check.py` is a development audit of the supplied unmodified script. To rerun it, clone both supplied repositories to a sibling `upstream` directory as in the original workspace; the main app and tests are fully self-contained and use the included `vendor` assets.

## Classroom distinctions

- **Image noise** is corruption of pixels; **distractor boxes** are real scene objects.
- **Segmentation** labels matching pixels; **detection** finds and validates an object region.
- **DIP** filters and transforms images; **perception** interprets regions as objects and estimates pose. The boundary is practical rather than absolute.
- **Localization** maps pixels to a physical pose; **IK** maps a desired hand pose to joint values.
- **Planning** chooses a safe sequence; **control** makes joints follow commands.
